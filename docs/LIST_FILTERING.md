# List Filtering & Search

The frontend (sibling repo `Norbiz-Web`, see its `CLAUDE.md`) drives these requirements — check there when a list-page task's backend shape is unclear.

- Column filters must be backend-side, case-insensitive partial-match ("contains") queries, one filter per column, combined with AND.
- Repositories backing a filterable list should extend `JpaSpecificationExecutor<T>` in addition to `JpaRepository<T, Long>`. Compose filters via `com.chardizard.Norbiz.util.SpecificationUtils` (`containsIgnoreCase`, `anyContainsIgnoreCase`, `allOf`) rather than hand-rolling a derived-name/`@Query` method per filter combination — this is the established pattern going forward (see `ItemRepository`/`ItemService` for the initial wiring).
- Date-type columns must support range filtering (`from`/`to` query params resolved to actual dates). The frontend resolves canned ranges (Today, Current Week, Current Month, Last 30 Days, Last 3 Months, Current Year) to concrete dates client-side — the backend only ever receives `from`/`to`, never a range label.
- The frontend's "Global Filter" search box is frontend-only (searches already-fetched page data, including hidden columns) — do **not** build a backend endpoint or query param for it.
- Spreadsheet export (list/report pages) exports **all rows matching the current column filters, across every page** — not just the page on screen. There is no separate export endpoint: the frontend's `fetchAllContent` pages through the normal list endpoint (same filter params) until `last=true`. `spring.data.web.pageable.max-page-size=1000` caps each request (larger `size` is silently clamped), so callers must loop rather than ask for one huge page. Any new list/report endpoint must therefore keep stable ordering across pages and honour the same filter params for every page.

## Dropdown lookups (`/lookups/*`)

Forms (transactions and master data) load their dropdowns from `LookupController`, not from the full list endpoints, so a user who can e.g. create a Purchase Order doesn't also need `VIEW_SUPPLIER`.

- **Access**: `@PreAuthorize("@lookupAccess.can(authentication, 'X')")`. `LookupAccess` maps each lookup to the entity's own `VIEW_` permission **plus** every permission whose form references that entity. **When a new transaction type or form starts referencing an entity, add its CREATE_/UPDATE_ permission to that map** — otherwise its users get 403 on the dropdown.
- **Payload**: slim only — `LookupResponse` (id, companyId, code, name, active) for master data; `ItemLookupResponse` adds `tags` and `costPrice` (null unless `VIEW_COST_PRICE`); `TransactionLookupResponse` (id, referenceNumber, date, supplier/warehouse id+name, purchaseOrderId, voided, loaded, and the `lines` a consuming form copies/receives against — line `costPrice` likewise gated). Only add a field when a form needs it, never contacts or audit fields, and gate anything sensitive by its existing permission; that's what keeps widening access safe.
- **Scoping**: every list lookup returns exactly **one** company's records — `companyId` query param (the form's company), falling back to the `X-Company-Id` header (the session's active company); 400 if neither is present. The company is access-checked (`assertCompanyAccess`; SUPER_ADMIN bypasses). By-id variants (`/lookups/x/{id}`) resolve a saved selection — including inactive ones — and call `assertCompanyAccess` on the record's company. Users are scoped to members of the requested company; Roles are system-wide (no company).
- **Params**: `q` (contains over code/name, max 255), `activeOnly` (default `true`), `tag` on `/items` (e.g. `INVENTORY`), `openOnly` for `/purchase-orders` and `/purchase-invoices` (default `true`: not voided, not fully loaded; invoices also Direct-mode only). Paginated, 50/page, default-sorted by name (transactions: newest first).
- Lookups only trim the option list. The consuming service must still validate that each referenced id belongs to the transaction's company **and is active** (see `docs/TRANSACTIONS.md` → inactive references).
